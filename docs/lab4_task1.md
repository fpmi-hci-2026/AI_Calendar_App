### Шаг 1. Определение действующих лиц (Акторов)

В нашей системе (с учетом разработанного API) можно выделить следующих акторов:
1.  **Гость** — неавторизованный пользователь (может только регистрироваться и входить).
2.  **Пользователь** (Студент, Специалист, Преподаватель) — авторизованный пользователь, работающий со своими данными.
3.  **AI-Ассистент** — системный актор (программа), который через MCP-сервер или внутренние вызовы обрабатывает запросы пользователя и обращается к API для чтения или записи данных.
4.  **Администратор** (перспектива) — управляет системой.

#### Пример спецификации Use Case для Wiki

**UC 2.1. Создание события**

*   **Актор:** Пользователь (авторизованный).
*   **Предусловие:** Пользователь авторизован в системе (имеет валидный JWT-токен).
*   **Основной поток:**
    1.  Пользователь отправляет POST-запрос на `/api/events/` с данными: `title`, `date`, `start_time`, `end_time`.
    2.  API проверяет валидность JWT-токена.
    3.  API валидирует входные данные (например, формат даты).
    4.  API создает новую запись в таблице `events` в базе данных.
    5.  API возвращает статус `201 Created` и JSON-объект созданного события с присвоенным `id`.
*   **Альтернативный поток (Ошибка валидации):**
    *   3а. Если дата указана в неверном формате или отсутствует заголовок, API возвращает статус `422 Unprocessable Entity` с описанием ошибки.
*   **Постусловие:** Событие сохранено в БД и будет отображаться в расписании пользователя.
